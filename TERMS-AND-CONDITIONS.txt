6. CPU AND GPU THERMAL LOAD TESTING

The CPU & GPU Thermal Load Test deliberately creates sustained processor and graphics-rendering activity. It is intended as a short, supervised diagnostic to observe temperature rise, fan response, thermal throttling and cooler behaviour.

The test may increase temperatures, fan speed, power consumption and system noise, and may expose pre-existing cooling, power, driver or hardware instability. It must not be left unattended. Stop immediately if there is unusual noise, smell, smoke, display corruption, severe throttling, instability or any other sign of unsafe operation.

The Software requires relevant temperature telemetry before starting a selected load and attempts to stop when the configured temperature limit is reached, telemetry becomes unavailable, the selected duration ends or the test window closes. For integrated-only graphics that share the processor package, the Software may use the CPU package temperature as the graphics safety sensor when no separate integrated-GPU temperature is exposed. Dedicated, hybrid or unclassified graphics configurations still require separate GPU temperature telemetry. These safeguards depend on sensor, driver, operating-system and application responsiveness and cannot guarantee that hardware will remain below a particular temperature or avoid damage.

The CPU stop-temperature control can be set as high as 105 °C. Depending on the processor, this may be at or above its thermal-throttling or maximum operating threshold. Selecting a high stop temperature does not mean that the temperature is safe for a particular system; the user remains responsible for choosing an appropriate limit and stopping the test immediately if unsafe behaviour is observed.

The built-in GPU workload uses WPF/Direct3D hardware rendering when Windows reports an available rendering tier. It is not a vendor-specific maximum-power benchmark and may not fully load every GPU or multi-GPU configuration. Test results are diagnostic observations, not certification of cooling capacity, stability or future reliability.

7. NETWORK MONITORING AND SCANNING

The Software may discover and monitor devices by using network technologies such as ICMP/ping, DNS, ARP and TCP connectivity checks.

The Software may record technical information including:

- IP addresses
- MAC addresses
- Hostnames
- User-assigned device names
- Response times
- Online/offline status
- Connection timestamps
- Connection incidents
- Open TCP ports
- Network diagnostic results

Device availability is generally determined through network reachability. An unreachable device does not necessarily mean that the computer was shut down or restarted.

Where the Software identifies a shutdown/restart event based solely on loss and restoration of network connectivity, that event should be considered an inferred diagnostic event, not confirmation of the actual cause.

The Network Speed & Bandwidth feature can report negotiated Ethernet/Wi-Fi link information without internet access. For public internet testing, the Software opens the official FAST.com website in the user's default browser; the speed test itself is performed by FAST.com/Netflix and is subject to that service's availability and terms. FAST.com may receive the connection's public IP address and normal browser/network metadata. For local-network testing, the Software can temporarily run a TCP throughput server on one authorised PC and send/receive generated in-memory test data from another authorised PC on the LAN. The LAN test does not read, transfer or upload local user files, but it may generate substantial network traffic for the selected test duration. Internet and LAN throughput tests run only when explicitly started by the user.
